- [2026-08-16] [M] No warning before a cache-invalidating action. Prompt caching is a prefix match, so several cockpit controls silently throw away the session's warm cache and the user only finds out afterwards, via the stats strip's hit rate dropping. Three tiers, worst first: (a) tool-set changes - MCP toggle/reconnect and reload-plugins - tools render at prefix position 0, so any add/remove/reorder invalidates tools + system + messages; (b) model switch - caches are model-scoped, so the whole prefix is gone; (c) thinking budget/display - invalidates the messages cache only, tools + system survive. usage.js's accumulator already tracks `cacheReadTokens`, so the cost of the impending re-write is computable at click time: warn (inline, `.mcp-error` pattern) when the session has more than some threshold of cached tokens, naming which of the three tiers applies. Scope/approach not designed: where the threshold sits, whether it's a confirm dialog or a passive note, and whether the warning belongs on the control or in the stats strip. The cockpit cannot set `cache_control` itself - prompt assembly belongs to the Agent SDK's `query()` - so avoiding needless invalidation is the only lever; do not let the copy imply we could extend the TTL. Separately, do not attribute plain idle-gap expiry (the default cache TTL is 5 minutes, refreshed on every read) to a user action - a warning that cries wolf after a coffee break is worse than none.

- [2026-08-18] [M] MCP "needs-auth" badge now has an "Authenticate" link (mcp-panel.js) once one actually appears - design decision made: the SDK exposes exactly one mechanism for this, `onElicitation` (mode 'url', a `url` to open in-browser; completion arrives later as a separate `elicitation_complete` system message, not synchronously). Wired end to end: session.js's onElicitation stores the pending {url, message} per server name and fire-and-forget-accepts (form-mode elicitation is declined outright - no UI for arbitrary JSON-schema forms, out of scope); session-registry.js's getMcpServerStatus merges it into the SDK's own status list as authUrl/authMessage and pushes a live `cockpit:mcp-auth` broadcast so a settings modal left open through the flow doesn't sit on a stale badge. Unit-covered at both layers (session.test.mjs, session-registry.test.mjs). **Not hand-verified live** - this sandbox has no real OAuth-requiring MCP server. If it doesn't work against a real needs-auth server (wrong field names, mode assumptions, elicitation firing before vs. after 'needs-auth' status, etc.), that's the first thing to check.
