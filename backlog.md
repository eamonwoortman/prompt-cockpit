## [H] Potentially bad

- [2026-09-02] Claude's transport is still outside `child-tracker.js`, and on Windows the SDK does not kill it. The SDK's own exit cleanup is `if (process.platform === "win32") try { e.stdin.end() } catch {} else e.kill("SIGTERM")` (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs`) - so on the platform this repo actually targets, a Ctrl-C closes the transport's stdin and hopes. Excluding Claude from process ownership was a deliberate scope decision (the auto-pilot design spec's Decision 7), not a claim that the SDK guarantees teardown, so this is a real residual gap: if a Claude transport is ever observed surviving exit on Windows, the fix is to retain its PID like Grok's and Codex's, next to the `spawnClaudeCodeProcess` follow-up. Needs a measurement first - watch for a surviving `claude`/node transport after Ctrl-C with a live Claude session - rather than widening scope on suspicion.

- [2026-09-02] Two short-lived `grok` spawns are untracked, so a Ctrl-C at the wrong moment leaks one: `src/grok-cli.js` (the capability/model probes, killed on a timeout only) and `rewindGrokSession`'s helper connection in `src/grok-session.js` (killed in a `finally`, which a `process.exit` never reaches). Both are seconds-long rather than session-length, so the exposure is one stray agent process, not a running turn - but a rewind is exactly when a user is likely to be impatient. Retaining them means `retain`/`release` around two more spawn sites; the awkward part is that `grok-cli.js` has no long-lived handle to hang the release off, so it wants a small `withTrackedSpawn` wrapper rather than another copy of the same four lines.

- [2026-09-02] `startGrokSession`'s connect/initialize failure path sets `closed = true` without killing the agent it just spawned, and `close()` then early-returns on that flag - so a `grok agent stdio` process whose `initialize` or `session/new` failed while the process itself stayed alive survives until `shutdown()`. Now bounded (the pid is tracked, so shutdown kills it), but it should not need shutdown to notice: the catch should tear the connection down the way `close()` does.

- [2026-09-02] `runtime.json`'s foreign-entry handling is liveness-only in both directions, and one of them loses the entry for good. `child-tracker.js`'s `belongsToAnotherInstance` decides whether to carry another cockpit's row forward by asking only whether that cockpit's PID is alive *right now*, and `persist()`'s transform keeps only rows that pass it. So: cockpit B boots, correctly leaves cockpit A's live CLI alone as `foreign`; A then crashes; B's very next `retain`/`release` re-evaluates, sees A's PID gone, and drops A's row from the file **without anything ever killing A's CLI**. A's paid agent is now running with no record in any cockpit's `runtime.json`, so no future boot will reap it. The other direction (a recycled owner PID making a dead instance look alive) self-heals at the next boot; this one does not, because there is nothing left to heal. Not a regression - the previous whole-file rewrite erased it too - but the fix is cheap and the disposition already exists in the code: preserve any non-adjudicated row whose `ownerPid` is not ours regardless of owner liveness, and let the next boot's `reapOrphans` adjudicate it, exactly as `carried` is already treated. Only bites with two concurrent cockpits, which `README.md`'s `PORT=4318` note actively invites.

- [2026-09-04] Final fix wave, item 5(c): a Grok pilot's own crashed-but-still-billing session can fail to block that pilot from firing again, because orphan-blocks-firing depends on a carried entry's `pilotIds` having been recorded, and `src/grok-session.js:139`'s `tracker.retain(...)` call passes no `pilotId` at all. Grok's `trackedPid` is assigned in an async IIFE, so a pilot's id is only attached to the tracker entry on the *next* `reviewRuns` heartbeat pass - up to 15s later - and never if the cockpit dies before that pass runs. `orphanPilotIds()` is `carried.flatMap(e => e.pilotIds || [])`, so an entry with no `pilotIds` blocks nothing: a Grok pilot can fire alongside its own live, billing orphan from an unclean exit, exactly the failure spec Risk 3's mitigation exists to prevent (see the spec's Risks section, updated in the same fix wave). Fix wants `retain(...)` at that call site to carry the pilotId synchronously where it is already known, or to attach it the instant the pid appears rather than gating on a heartbeat - mirroring how `fire()` already stamps `runs.get(pilot.id).sessionId` eagerly for the same class of reason (src/autopilot.js).
