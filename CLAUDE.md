# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Prompt Cockpit: a local browser UI for driving a Claude Code or Grok CLI session against a project folder. Plain Node.js server (no framework, no bundler) + vanilla JS frontend (no build step). It talks to the CLIs over their SDKs/protocols, not by wrapping a terminal. The server binds to `127.0.0.1` only and is not meant to be exposed to the network.

## Commands

```
npm install       # first time only
npm start          # runs src/server.js, http://localhost:4317 (PORT env overrides)
npm test           # node --test tests/*.test.mjs - fast, no network, no CLI spawned
node --test tests/session.test.mjs          # run a single test file
node tests/integration.manual.mjs           # NOT part of npm test - spawns a real Haiku session via the SDK, costs a few cents, ~10-20s. Run by hand after touching src/session.js.
```

Other `tests/*.manual.mjs` files (`grok-rewind-strings.manual.mjs`, `grok-rewind-probe.manual.mjs`, `grok-live.manual.mjs`) are similarly excluded from `npm test` and require a real CLI/session - run individually with `node tests/<file>`.

Read `tests/README.md` before touching test coverage - it documents, feature by feature, exactly what's unit-tested vs hand-verified-only and why (mostly: anything that touches the real SDK's non-injectable functions, like `getSessionMessages`/`forkSession`, or is pure client-side DOM/websocket behavior with no jsdom in this project).

## Architecture

**Two providers, one shape.** Claude (`src/session.js`, via `@anthropic-ai/claude-agent-sdk`'s `query()`) and Grok (`src/grok-session.js`, via `grok agent stdio` / ACP) are driven by structurally parallel modules and normalized into the same handle shape by `src/session-registry.js`, so the rest of the server and the entire frontend mostly don't care which provider a session uses. Provider-specific quirks live in `grok-*.js` files (`grok-acp.js` protocol plumbing, `grok-messages.js` message translation, `grok-rewind.js`, `grok-history.js`, `grok-extensions.js`, `grok-launcher.js`) mirroring their Claude counterparts (`rewind.js`, `session-history.js`, `session-launcher.js`).

**`src/session-registry.js` is the live in-memory hub.** One row per running cockpit session, keyed by a cockpit-minted UUID (not the provider's own session id, which is mutable and refreshed as messages arrive). Rows are purely ephemeral - nothing here touches disk, and a row disappears when its session closes or the process restarts.

**Four separate state stores, deliberately not unified** (see the boundary comment atop `session-registry.js`):
- In-memory registry rows (above) - live SDK-reported state (model, mode, thinking budget, usage).
- `public/settings.js` (browser `localStorage`) - per-browser UI prefs, never sent to the server.
- `session-defaults.js` + `plugin-settings.js` + `session-titles.js` + `permission-rules.js` + `git-commit-guard.js` (all under the target project's own `.claude/settings.local.json`) - per-project prefs that survive a restart and are shared across every tab/browser pointed at that cwd. `server.js` is what bridges live registry state into this store (see `seedSessionDefaults()` and the `thinking`/`auto-continue`/`title` routes) - it's the only layer that's supposed to know both stores exist.
- `~/.prompt-cockpit/` - cockpit's own durable files, scoped to the *user*, not to a project or an instance: `operator-token` (`operator-auth.js`), `runtime.json` (`child-tracker.js`), and, on this branch, `autopilots.json` (`autopilot-store.js`), `autopilot-log.jsonl` (`autopilot-log.js`), `provider-cooldowns.json` (`provider-cooldowns.js`, the durable provider rate-limit cooldown store that auto-pilot's back-off reads) and `superagent/` (`config.json`, `jobs/<id>/events.jsonl` + `state.json` + `ledger/`, `worktrees/`; see the superagent paragraph below). Not settings; `runtime.json` is a crash-recovery record. Being per-user is the sharp edge - a second cockpit on another `PORT` reads and writes the same `runtime.json`, which is why its entries carry `ownerPid`/`ownerStartedAt` and why writes are read-modify-write rather than whole-file. Override the paths with `COCKPIT_OPERATOR_FILE` / `COCKPIT_RUNTIME_FILE` so tests never touch the real home. The broader `COCKPIT_HOME` redirects `autopilot-store.js`, `autopilot-log.js`, `provider-cooldowns.js` and `child-tracker.js` only - `operator-auth.js` does not read it, so a test setting only `COCKPIT_HOME` still mints `operator-token` into the real home unless `COCKPIT_OPERATOR_FILE`/`COCKPIT_OPERATOR_TOKEN` is also set. `COCKPIT_RUNTIME_FILE` takes precedence over `COCKPIT_HOME` for `runtime.json` specifically.

**`src/server.js`** is the whole HTTP + WebSocket surface, hand-rolled (no router library). Two auth layers stacked: (1) every request is checked against `Host`/`Origin` allowlists (`isSpoofedRequest`) since `127.0.0.1` binding alone doesn't stop a browser page from making cross-origin requests to it or defeat DNS rebinding; (2) session-scoped routes additionally require a per-session bearer token minted at session creation (`registry.checkToken`). `/api/browse`, `/api/resumable`, `/api/history/*` are intentionally token-free (read-only, no live session to gate against) but still Origin/Host-checked. Live turns stream over one WebSocket per session (`/ws?id&token`), with `since=<seq>` supporting gapless reconnect via `src/event-log.js`'s replay buffer.

**Input is a push-queue, not a call-and-response.** `session.js`'s `createInputQueue()` feeds `query()`'s `AsyncIterable` prompt; sending a message while a turn is still running just enqueues it (visible client-side as the queue panel) rather than dropping or interleaving. A known SDK quirk this works around: `query()` never emits `system/init` until the iterable's first `.next()` resolves, so a startup sentinel is pushed immediately to unblock it (see `.claude/memory/sdk-streaming-input-gotchas.md` for this and a second uuid-related gotcha - re-read that note before touching `session.js`/`rewind.js`, especially across an SDK version bump, since these are undocumented internals with no deprecation contract).

**Rewind = fork, not mutate.** `rewind()` (`rewind.js` for Claude, `grok-rewind.js`/`grok-session.js`'s `rewindGrokSession` for Grok) forks the underlying conversation at a target turn into a *new* provider-side session, which `server.js`'s rewind route then wraps in a brand-new cockpit registry row (inheriting model/mode/thinking-budget/auto-continue from the row being forked, not the cwd's persisted defaults - see `seedSessionDefaults`'s call in that route). The original session and its row are untouched.

**Frontend (`public/`)** is one `app.js` entry point wiring together focused, dependency-injected-by-import modules - no bundler, loaded as native ES modules directly by `index.html`. Rough split: `stream-view.js` (rendering), `compose.js`/`file-picker.js` (input), `dir-browser.js`/`diff-view.js` (modals), `stats-panel.js`/`turn-chart.js` (live cost/token strip), `history-pane.js`/`history-search.js` (past sessions), `queue-panel.js`, `mcp-panel.js`/`plugin-panel.js`/`settings.js` (gear menu), `autopilot-panel.js`/`autopilot-form.js` (Pilots/Logs pane and its create/edit modal), `notifications-panel.js` (bell + attach flow), `autopilot-format.js` (pure formatters). `detail-pane.js` docks beside the transcript and, beyond its original Summary/Payload/Result/Timing tabs for the selected tool call, also hosts two independent tabs unrelated to tool-call selection: Tasks (the live task list, entry point next to the cost-graph toggle) and Agent (a subagent's own transcript, tailed live in place of the old `agent-view.html` pop-out tab). `src/permissions.js` (permission-mode cycle order), `src/stream-join.js` (Grok token-join whitespace) and `src/autopilot-schedule.js` (next-run due-ness) are shared verbatim between server and browser (see `SHARED_SRC_FILES` in `src/static-files.js`) rather than duplicated.

**Pricing** (`src/pricing.json`, `src/pricing_grok.json`) is a static local copy, not fetched live - `usage.js`'s `costForUsage` returns `null` (not a guess) for an unpriced model.

**Cockpit owns the CLI processes it spawns, and exits through one door.** Grok and Codex are spawned by cockpit itself, and a paid agent left running after a Ctrl-C is a real bill, so `src/child-tracker.js` records every such PID in `~/.prompt-cockpit/runtime.json` and `src/shutdown.js` is the single idempotent async teardown every exit route (TTY Ctrl-C keypress, `SIGINT`, `SIGTERM`, `SIGBREAK`) goes through. Three rules keep it honest:
- **Tracked per process, not per session.** One Codex app-server backs every Codex session, so retain/release lives at the spawn (`codex-app-server.js`, `grok-session.js`'s `connectImpl` call) and release fires from the child's own `'exit'`/`'error'` as well as from an explicit close. Tying it to session close instead meant the last session closing un-tracked a process that was still billing, which made `shutdown()` skip its grace period *and* its force-kill pass.
- **Verification refuses rather than guesses.** A recorded PID is only killed once its OS-reported start time still matches (`ps -o lstart` / `Get-Process`, 3s tolerance) *and* the cockpit that recorded it is provably gone. Killing the operator's editor because a PID got recycled is worse than logging an orphan; an orphan it declines to kill blocks that auto-pilot instead (`orphanPilotIds`).
- **Claude is deliberately out of scope.** The agent SDK spawns and reaps its own transport - except that on Windows its exit handler only calls `stdin.end()`, so that is a known residual gap in `backlog.md`, not a claim of coverage.

**Auto-pilot is a supervisor, not `/loop`.** `src/autopilot.js`'s `createAutopilot()` runs ONE ~15s heartbeat that reviews every configured pilot and every live run - not a timer per pilot, and nothing iterates inside a single conversation. Each firing spawns a brand-new cockpit session, sends one stored prompt, and force-closes it once the turn goes idle. The concurrency lock is `autopilot.js`'s own `runs` map, keyed by pilot id and mutated in place across every `await` - not a PID: a PID only proves a process exists, where the registry row is what actually knows whether a session is running, blocked on an approval, or idle. Wiring into cockpit's boot and shutdown sequence goes through exactly two generic hooks - `src/shutdown.js`'s `onBeforeClose`/`onAfterClose` - plus the same `retain`/`attachPilot`/`orphanPilotIds` surface `child-tracker.js` already exposed for process ownership; `src/autopilot-wiring.js`'s `wireAutopilot({ shutdown, autopilot, tracker, cooldowns })` is the one place that composes them (it also loads `cooldowns` before auto-pilot starts and flushes it in the after-close hook; `server.js` feeds it from the registry's `addRateLimitListener`), so that neither `shutdown.js` nor `child-tracker.js` has to know a pilot exists. `session-registry.js` is equally kept in the dark on purpose: `handleApprovalRequest`'s interceptors (`addApprovalInterceptor`, with `setApprovalInterceptor` kept as auto-pilot's legacy single slot; likewise `addSessionRemovedListener`/`setSessionRemovedListener`) are plain callbacks the registry would fire for a human just the same, and a pilot's own config/history (`autopilots.json` / `autopilot-log.jsonl`, via `autopilot-store.js` / `autopilot-log.js`) lives entirely outside the registry's four state stores above. The UI ships as four `public/` modules - `autopilot-panel.js` (the Pilots/Logs pane), `autopilot-form.js` (the create/edit modal), `notifications-panel.js` (the bell and the token-free `?attach=` flow) and `autopilot-format.js` (pure presentation helpers) - plus `style-autopilot.css`. `src/autopilot-schedule.js` is served verbatim to the browser via `SHARED_SRC_FILES`, so the pane's "next run" label and the supervisor's own due-ness check are literally the same code and cannot drift.

**Superagent is a library, not yet a feature.** `src/superagent/` (config, store, worktree, results, prompts, sequencer, runner, and `createSuperagent` in `index.js`) drives a job through the `milestone-1` author -> human fixture on its own heartbeat, separate from auto-pilot's, and is not wired into `src/server.js`. Only `author` and `human` phase kinds run; router, verifier, review loops, per-task implementation, the usage (cost) ledger and worktree removal do not exist yet (`ledger/` above is only the archived per-job ledger directory). `src/session.js` accepts `sdkOptions.hooks` (merged after cockpit's own) and `sdkOptions.interceptEveryPermission` for it; whether `auto` mode really routes ordinary tools through `canUseTool` is unproven until `tests/superagent-two-phase.manual.mjs` is run.

`src/json-store.js` underneath all of this is `settings-file.js`'s atomic write (tmp + rename, Windows unlink-first), corrupt-file refusal and per-path serialized read-modify-write, extracted so cockpit's own files get the same guarantees a project's `settings.local.json` already had. `settings-file.js` keeps its API and delegates. Use `updateJson` when the payload is mutated in place and a corrupt file must be refused; `replaceJson` when it is rebuilt wholesale and a corrupt file must be replaced (that is `runtime.json`, where refusing would silently stop recording PIDs).
