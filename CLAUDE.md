# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Prompt Cockpit: a local browser UI for driving a Claude Code or Grok CLI session against a project folder. Plain Node.js server (no framework, no bundler) + vanilla JS frontend (no build step). It talks to the CLIs over their SDKs/protocols, not by wrapping a terminal. The server binds to `127.0.0.1` only and is not meant to be exposed to the network.

## Commands

```
npm install       # first time only
npm start          # runs src/server.js, http://localhost:4317 (PORT env overrides)
npm test           # node --test tests/*.test.mjs - fast, no network, no CLI spawned
node --test tests/session.test.mjs          # run a single test file
node tests/integration.manual.mjs           # NOT part of npm test - spawns a real Haiku session via the SDK, costs a few cents, ~10-20s. Run by hand after touching src/session.js.
```

Other `tests/*.manual.mjs` files (`grok-rewind-strings.manual.mjs`, `grok-rewind-probe.manual.mjs`, `grok-live.manual.mjs`) are similarly excluded from `npm test` and require a real CLI/session - run individually with `node tests/<file>`.

Read `tests/README.md` before touching test coverage - it documents, feature by feature, exactly what's unit-tested vs hand-verified-only and why (mostly: anything that touches the real SDK's non-injectable functions, like `getSessionMessages`/`forkSession`, or is pure client-side DOM/websocket behavior with no jsdom in this project).

## Architecture

**Two providers, one shape.** Claude (`src/session.js`, via `@anthropic-ai/claude-agent-sdk`'s `query()`) and Grok (`src/grok-session.js`, via `grok agent stdio` / ACP) are driven by structurally parallel modules and normalized into the same handle shape by `src/session-registry.js`, so the rest of the server and the entire frontend mostly don't care which provider a session uses. Provider-specific quirks live in `grok-*.js` files (`grok-acp.js` protocol plumbing, `grok-messages.js` message translation, `grok-rewind.js`, `grok-history.js`, `grok-extensions.js`, `grok-launcher.js`) mirroring their Claude counterparts (`rewind.js`, `session-history.js`, `session-launcher.js`).

**`src/session-registry.js` is the live in-memory hub.** One row per running cockpit session, keyed by a cockpit-minted UUID (not the provider's own session id, which is mutable and refreshed as messages arrive). Rows are purely ephemeral - nothing here touches disk, and a row disappears when its session closes or the process restarts.

**Four separate state stores, deliberately not unified** (see the boundary comment atop `session-registry.js`):
- In-memory registry rows (above) - live SDK-reported state (model, mode, thinking budget, usage).
- `public/settings.js` (browser `localStorage`) - per-browser UI prefs, never sent to the server.
- `session-defaults.js` + `plugin-settings.js` + `session-titles.js` + `permission-rules.js` + `git-commit-guard.js` (all under the target project's own `.claude/settings.local.json`) - per-project prefs that survive a restart and are shared across every tab/browser pointed at that cwd. `server.js` is what bridges live registry state into this store (see `seedSessionDefaults()` and the `thinking`/`auto-continue`/`title` routes) - it's the only layer that's supposed to know both stores exist.
- `~/.prompt-cockpit/` - cockpit's own durable files, scoped to the *user*, not to a project or an instance: `operator-token` (`operator-auth.js`), `runtime.json` (`child-tracker.js`), and, on this branch, `autopilots.json` (`autopilot-store.js`), `autopilot-log.jsonl` (`autopilot-log.js`), `provider-cooldowns.json` (`provider-cooldowns.js`, the durable provider rate-limit cooldown store that auto-pilot's back-off reads) and `superagent/` (`config.json`, `owner.lock`, `jobs/<id>/events.jsonl` + `state.json` + `ledger/`, `worktrees/`; see the superagent paragraph below). Not settings; `runtime.json` is a crash-recovery record. Being per-user is the sharp edge - a second cockpit on another `PORT` reads and writes the same `runtime.json`, which is why its entries carry `ownerPid`/`ownerStartedAt` and why writes are read-modify-write rather than whole-file. Override the paths with `COCKPIT_OPERATOR_FILE` / `COCKPIT_RUNTIME_FILE` so tests never touch the real home. The broader `COCKPIT_HOME` redirects `autopilot-store.js`, `autopilot-log.js`, `provider-cooldowns.js`, `child-tracker.js` and the superagent modules only (`src/superagent/config.js`'s `defaultSuperagentRoot()` is `<COCKPIT_HOME or home>/.prompt-cockpit/superagent`; `store.js` defaults its jobs root to `<that>/jobs`, `config.js` its `config.json` to `<that>/config.json`, and `index.js` its worktrees root to `<that>/worktrees`) - `operator-auth.js` does not read it, so a test setting only `COCKPIT_HOME` still mints `operator-token` into the real home unless `COCKPIT_OPERATOR_FILE`/`COCKPIT_OPERATOR_TOKEN` is also set. `COCKPIT_RUNTIME_FILE` takes precedence over `COCKPIT_HOME` for `runtime.json` specifically.

**`src/server.js`** is the whole HTTP + WebSocket surface, hand-rolled (no router library). Two auth layers stacked: (1) every request is checked against `Host`/`Origin` allowlists (`isSpoofedRequest`) since `127.0.0.1` binding alone doesn't stop a browser page from making cross-origin requests to it or defeat DNS rebinding; (2) session-scoped routes additionally require a per-session bearer token minted at session creation (`registry.checkToken`). `/api/browse`, `/api/resumable`, `/api/history/*` are intentionally token-free (read-only, no live session to gate against) but still Origin/Host-checked. Live turns stream over one WebSocket per session (`/ws?id&token`), with `since=<seq>` supporting gapless reconnect via `src/event-log.js`'s replay buffer.

**Input is a push-queue, not a call-and-response.** `session.js`'s `createInputQueue()` feeds `query()`'s `AsyncIterable` prompt; sending a message while a turn is still running just enqueues it (visible client-side as the queue panel) rather than dropping or interleaving. A known SDK quirk this works around: `query()` never emits `system/init` until the iterable's first `.next()` resolves, so a startup sentinel is pushed immediately to unblock it (see `.claude/memory/sdk-streaming-input-gotchas.md` for this and a second uuid-related gotcha - re-read that note before touching `session.js`/`rewind.js`, especially across an SDK version bump, since these are undocumented internals with no deprecation contract).

**Rewind = fork, not mutate.** `rewind()` (`rewind.js` for Claude, `grok-rewind.js`/`grok-session.js`'s `rewindGrokSession` for Grok) forks the underlying conversation at a target turn into a *new* provider-side session, which `server.js`'s rewind route then wraps in a brand-new cockpit registry row (inheriting model/mode/thinking-budget/auto-continue from the row being forked, not the cwd's persisted defaults - see `seedSessionDefaults`'s call in that route). The original session and its row are untouched.

**Frontend (`public/`)** is native ES modules with no bundler: `index.html` loads `entry.js`, which imports `superagent-view.js` on `?view=superagent` and `app.js` otherwise, and `app.js` wires together focused, dependency-injected-by-import modules. Rough split: `stream-view.js` (rendering), `compose.js`/`file-picker.js` (input), `dir-browser.js`/`diff-view.js` (modals), `stats-panel.js`/`turn-chart.js` (live cost/token strip), `history-pane.js`/`history-search.js` (past sessions), `queue-panel.js`, `mcp-panel.js`/`plugin-panel.js`/`settings.js` (gear menu), `autopilot-panel.js`/`autopilot-form.js` (Pilots/Logs pane and its create/edit modal), `notifications-panel.js` (bell + attach flow), `autopilot-format.js` (pure formatters), `entry.js` (what `index.html` loads: imports `/superagent-view.js` on `?view=superagent` and `/app.js` otherwise, so the Superagent tab never rejoins a session) and `superagent-view.js` (that tab: jobs, a status and artifact pane, the needs-you pane, the router panel). `detail-pane.js` docks beside the transcript and, beyond its original Summary/Payload/Result/Timing tabs for the selected tool call, also hosts two independent tabs unrelated to tool-call selection: Tasks (the live task list, entry point next to the cost-graph toggle) and Agent (a subagent's own transcript, tailed live in place of the old `agent-view.html` pop-out tab). `src/permissions.js` (permission-mode cycle order), `src/stream-join.js` (Grok token-join whitespace), `src/autopilot-schedule.js` (next-run due-ness) and `src/notify-dedupe.js` (one browser notification per new entry across tabs: `localStorage` key `cockpit:notifiedKeys` under Web Lock `cockpit:notify`) are shared verbatim between server and browser (see `SHARED_SRC_FILES` in `src/static-files.js`) rather than duplicated.

**Pricing** (`src/pricing.json`, `src/pricing_grok.json`) is a static local copy, not fetched live - `usage.js`'s `costForUsage` returns `null` (not a guess) for an unpriced model.

**Cockpit owns the CLI processes it spawns, and exits through one door.** Grok and Codex are spawned by cockpit itself, and a paid agent left running after a Ctrl-C is a real bill, so `src/child-tracker.js` records every such PID in `~/.prompt-cockpit/runtime.json` and `src/shutdown.js` is the single idempotent async teardown every exit route (TTY Ctrl-C keypress, `SIGINT`, `SIGTERM`, `SIGBREAK`) goes through. Three rules keep it honest:
- **Tracked per process, not per session.** One Codex app-server backs every Codex session, so retain/release lives at the spawn (`codex-app-server.js`, `grok-session.js`'s `connectImpl` call) and release fires from the child's own `'exit'`/`'error'` as well as from an explicit close. Tying it to session close instead meant the last session closing un-tracked a process that was still billing, which made `shutdown()` skip its grace period *and* its force-kill pass.
- **Verification refuses rather than guesses.** A recorded PID is only killed once its OS-reported start time still matches (`ps -o lstart` / `Get-Process`, 3s tolerance) *and* the cockpit that recorded it is provably gone. Killing the operator's editor because a PID got recycled is worse than logging an orphan; an orphan it declines to kill blocks that auto-pilot instead (`orphanPilotIds`).
- **Claude is deliberately out of scope.** The agent SDK spawns and reaps its own transport - except that on Windows its exit handler only calls `stdin.end()`, so that is a known residual gap in `backlog.md`, not a claim of coverage.

**Auto-pilot is a supervisor, not `/loop`.** `src/autopilot.js`'s `createAutopilot()` runs ONE ~15s heartbeat that reviews every configured pilot and every live run - not a timer per pilot, and nothing iterates inside a single conversation. Each firing spawns a brand-new cockpit session, sends one stored prompt, and force-closes it once the turn goes idle. The concurrency lock is `autopilot.js`'s own `runs` map, keyed by pilot id and mutated in place across every `await` - not a PID: a PID only proves a process exists, where the registry row is what actually knows whether a session is running, blocked on an approval, or idle. Wiring into cockpit's boot and shutdown sequence goes through exactly two generic hooks - `src/shutdown.js`'s `onBeforeClose`/`onAfterClose` - plus the same `retain`/`attachPilot`/`orphanPilotIds` surface `child-tracker.js` already exposed for process ownership; `src/autopilot-wiring.js`'s `wireAutopilot({ shutdown, autopilot, tracker, cooldowns })` is the one place that composes them (it also loads `cooldowns` before auto-pilot starts and flushes it in the after-close hook; `server.js` feeds it from the registry's `addRateLimitListener`), so that neither `shutdown.js` nor `child-tracker.js` has to know a pilot exists. `session-registry.js` is equally kept in the dark on purpose: `handleApprovalRequest`'s interceptors (`addApprovalInterceptor`, with `setApprovalInterceptor` kept as auto-pilot's legacy single slot; likewise `addSessionRemovedListener`/`setSessionRemovedListener`) are plain callbacks the registry would fire for a human just the same, and a pilot's own config/history (`autopilots.json` / `autopilot-log.jsonl`, via `autopilot-store.js` / `autopilot-log.js`) lives entirely outside the registry's four state stores above. The UI ships as four `public/` modules - `autopilot-panel.js` (the Pilots/Logs pane), `autopilot-form.js` (the create/edit modal), `notifications-panel.js` (the bell and the token-free `?attach=` flow) and `autopilot-format.js` (pure presentation helpers) - plus `style-autopilot.css`. `src/autopilot-schedule.js` is served verbatim to the browser via `SHARED_SRC_FILES`, so the pane's "next run" label and the supervisor's own due-ness check are literally the same code and cannot drift.

**Superagent is a library wired into the server behind a host and a Superagent tab.** `src/superagent/` (config, store, worktree, results, prompts, sequencer, runner, and `router.js`, and `createSuperagent` in `index.js`) drives a job through the `milestone-1` (author -> human) or `milestone-2` (spec -> spec-review -> plan -> plan-review -> implement -> test -> accept, with review loops, a verifier, per-task implementation with task review, and test-failure routing) fixture, or the default pipeline (`createJob` with `fixture: null`: an automatic brainstorm, then `milestone-2`'s phases with the spec writer reading the brief), on its own heartbeat, separate from auto-pilot's. Runnable phase kinds are `author`, `brainstorm`, `review`, `per-task` and `human`. The automatic brainstorm runs one attempt per turn: the brainstormer asks up to 5 questions (purpose `ask`), then a read-only stand-in (role `stand-in`, `tools: ['Read', 'Grep', 'Glob']`, `disallowedTools: ['mcp__*']`, purpose `answer`) answers the batch tagged `from-idea`, `from-project` or `assumed` and returns its result as its final message, which the runner writes to `result.json` on the first scan that sees it; the stand-in's tool restriction and final-message result are unverified against the real SDK. The brainstormer finishes with `questions: []` and a brief carrying `## Assumptions made for you` and `## Your answers`, and in a brainstorming job the output of the first `author` phase that takes `brief` as an input (Feature's `spec`) must carry both headings too; `brainstormLog(job)` (`sequencer.js`) lists every exchange with its tag. A stand-in that cannot answer escalates one question as `needs-you`/`question` (`detail.kind: 'stand-in'`). `answerQuestion(jobId, text)` (1-4000 characters after trim) appends a `question-answered` event that sets the job running again and resumes the scope that asked; the answer reaches that scope's later cards as `userAnswers` (the brainstorm's as `exchanges`, tagged `from-you`), an answered verifier-confirmed blocker earns one extra review round, and `limits.questionsPerScope` (default 3) turns a scope's next question past the cap into `stuck` (`question-cap`). Every worker's ask, the brainstormer's `AskUserQuestion` included, is denied, so a question reaches the user only through `needs-you`. Each `attempt-ended` carries the attempt's `tokens` (the registry row's usage totals), which feed `limits.brainstormTokens`; it is an under-count only for attempts finished by reconcile after a restart (`tokens: null`), and a removed attempt keeps the last scanned snapshot. The router (`router.js`) is an isolated single-turn `query()` on an allowlisted model (`settingSources: []`, no tools or MCP, inline `settings.apiKeyHelper` copied from the user's `~/.claude/settings.json` plus `autoMemoryEnabled: false`, that file's `env` block merged over the process env so a gateway `ANTHROPIC_BASE_URL` reaches the call, own cwd under the superagent root; spike S4b) that picks `retry`, `retry-alternate`, `retry-handoff` or `escalate` for router-eligible failed attempts and records each call as a `router-decided` event; its token limit is a pre-send estimate, and any router failure escalates as `stuck`. It runs only when one is injected (`createSuperagent({ router })`; the default `null` keeps the code-only retries), the notification-text router call is not built, and manual mode, the usage (cost) ledger and usage caps, pause/resume, giving feedback or retrying a stuck job, a settings modal, and worktree removal (except the half-made worktree of a provisioning a Stop cancelled) do not exist yet (`ledger/` above is only the archived per-job ledger directory; the full deferred list, each with its later plan, is in `backlog.md` under "Superagent - planned for later plans"). Every `needs-you` state other than `ready-to-try`, an answerable `question` and the self-clearing `folder-changed` (below) stays terminal (`stuck`, including `why: 'tasks-invalid'`, and a `question` whose `detail.kind` is `'budget'`). `tests/superagent-pipeline.manual.mjs` (not run by implementers) is the real-model probe of `milestone-2`; with the SDK at 0.3.318 (Claude Code 2.1.318) the Opus roles run on `claude-opus-5-5` (older SDKs get a 400 "version 2.1.280 or newer is required"), and the 2026-11-05 run reached `ready-to-try` in 466 s, though review-fix rounds, the verifier, test routing, the brainstorm and answered questions have still only run under scripted workers. `src/session.js` accepts `sdkOptions.hooks` (merged after cockpit's own) and `sdkOptions.interceptEveryPermission` for it; the 2026-11-04 run of `tests/superagent-two-phase.manual.mjs` showed `auto` mode does NOT route Bash through `canUseTool` (Bash and `git commit` ran with no intercept), so the deny-every-ask rule only covers prompts the SDK actually asks, e.g. `AskUserQuestion`. The superagent test suite's temp repos set `core.fsmonitor false` because a system-level `core.fsmonitor=true` leaks one daemon per repo; `worktree.js`'s `defaultGit` passes `-c core.fsmonitor=false` for superagent's own git calls (not the workers'). The router's `routerMaxOutputTokens` limits its answer (output less thinking, since Haiku 5.5 always thinks), the hard `CLAUDE_CODE_MAX_OUTPUT_TOKENS` cap is that max + 1000 (`ROUTER_THINKING_ALLOWANCE`), and its `usage` keeps the request (`result.usage`, compared with the pre-send estimate) apart from the spend (`modelUsage`, which folds in a hidden ~2,951-token request). **Workflow files (Plan 7).** A job runs a workflow: a JSON file (`format: 1`, `id`, `name`, `description`, `artifacts`, `phases`, `roles`) from three sources, built-in `<cockpit>/workflows/*.json` (`feature.json`, `troubleshooting.json`, beside `prompts/superagent/`), global `<superagent root>/workflows/*.json` and project `<primary folder>/.superpowers/superagent/workflows/*.json`, loaded and validated by `src/superagent/workflows.js`. Project beats global beats built-in by `id`, compared case-insensitively (`sameWorkflowId`: precedence, same-source duplicates, the `config-pipeline` reservation, default selection and `createJob`'s lookup); an invalid or duplicated override is listed invalid and still shadows the lower sources, never silently replaced by them, and a broken file never stops the other workflows (a workflows folder that cannot be read, e.g. `EACCES`, is listed as one invalid entry for its source). `artifacts` maps keys to repo-relative paths with `{slug}`/`{date}` as the only placeholders, unique and outside the reserved namespaces (`.git/`, `.superpowers/superagent/`, `docs/superpowers/jobs/{slug}/reviews/` and `/tasks/`). A role's prompt is looked up as `<primary folder>/.superpowers/superagent/prompts/<role>.md`, then the workflow's own `prompt`, then `prompts/superagent/<role>.md` (`resolvePromptPath`). Models merge four layers, later winning: `defaultConfig().models` < the workflow's `roles.<role>` < `config.json` `defaults.models` < `projects[<path>].models`; the engine roles `verifier`, `stand-in` and `router` come from config only. `config.json`'s `pipeline` (deprecated) is offered as the reserved workflow `config-pipeline`, `custom (config.json)`, only when the raw file sets it. `createJob` records `workflow`, `artifacts` and `prompts` in `job-created` and never rereads the file; a recorded workflow prompt that has vanished ends the attempt `stuck` with `why: 'prompt-missing'`. The engine keys on phase properties, not names: an `author` phase with `test: true` (at most one, directly after the single `per-task` phase) routes failures into that phase, the `brainstorm` kind picks the brainstormer deny message, and artifact paths come from the job (`artifactPaths(job)`); jobs without `workflow` are normalised to `feature` and the fixed legacy table in `store.js`'s `deriveJob`. The Feature stand-in defaults to Sonnet now. `troubleshooting` is investigate (Opus, 80 turns) -> diagnosis-review (Opus, 40, up to 3 rounds) -> fix (`per-task`; fixer Sonnet 80 with Opus alternate, fix-reviewer Sonnet 80) -> verify (verifier-tester, Sonnet 80, `test: true`) -> accept, with no human checkpoint before accept. **In-place folders.** A folder row can be created with `inPlace` (route and library: an array of the job's folders; recorded per repo with `toplevel` and `admittedHead`), so the job runs in that folder on a new `superagent/<slug>` branch instead of a worktree (`src/superagent/inplace.js`). Before `job-created`, `checkInPlace` refuses with `ERR_FOLDER_BUSY_GIT` (detached HEAD, rebase/merge/cherry-pick/revert/bisect), `ERR_FOLDER_DIRTY` (only when `git status` cannot be read; uncommitted and untracked changes are admitted and recorded per repo as `pendingChanges` `{ paths (at most 200), total }`, shown on the worker card, and `contract.md` tells workers to stage by explicit path and never touch those paths, prompt-only like the other in-place rules), `ERR_FOLDER_ON_JOB_BRANCH` (a worktree job whose origin sits on a `superagent/*` branch is refused too), `ERR_BRANCH_EXISTS`, and the supervisor's in-memory reservation per repo top level (taken for every job's folders, in-place exclusive, worktree origins sharing; rebuilt from unfinished jobs at `start()`, resolving the top level of pre-Plan-7 repos through git) refuses with `ERR_FOLDER_IN_USE`; the route also maps `ERR_INVALID_REQUEST`, `ERR_UNKNOWN_WORKFLOW`, `ERR_INVALID_WORKFLOW`, `ERR_FOLDER_CHANGED`. Provisioning rechecks, then runs `git switch -c`, creates the ledger directory and appends `/.superpowers/superagent/<jobId>/` to the repo's `info/exclude` (no `.gitignore`), verified with `git check-ignore`; a failure after the switch fails the job and leaves the folder on the branch. Before every launch `checkGate` requires the branch, no git operation in progress and `baseSha` as an ancestor of HEAD (uncommitted changes allowed); otherwise nothing launches and the job is `needs-you` with `why: 'folder-changed'`, re-checked every heartbeat and cleared by a `folder-restored` event when the folder is back; a folder still bad but with a different text gets a fresh `folder-changed` (new `needsYouSeq`, so a new bell entry), an unchanged one appends nothing. The job card marks each in-place repo `inPlace: true` and `contract.md` forbids tree-wide git commands, branch switches and worktrees there, a prompt-only rule since `auto` mode does not route Bash through `canUseTool`. A gated attempt is not counted toward caps, repeated-error or back-off, and lists no artifacts. Stop, accept and failure leave the folder on the branch; the user's own sessions in it are not detected, and git calls have no timeout. **Wiring (Plan 6).** `src/superagent-host.js`'s `createSuperagentHost` is built `off` at module scope in `server.js` and goes `off -> initialising -> ready | not-owner | error -> stopping -> stopped`; `admit`/`read` gate the routes, and `stop()` and `afterClose()` share one 2500 ms budget (`HOST_STOP_DEADLINE_MS`) measured from `stop()`'s start, which is why `FORCE_EXIT_MS` is 10000 (3 + 1.5 + 2 + 2.5 = 9 s of comment budget). `src/superagent-wiring.js`'s `wireSuperagent({ shutdown, host })` registers `onBeforeClose`/`onAfterClose` before init, after `wireAutopilot` in the listen callback. **One owner per machine:** `src/superagent/owner-lock.js` holds `<superagent root>/owner.lock` (create-if-absent by atomic tmp write + `link`; a lock whose owner is provably dead is taken over by rename-to-claim), so a second Cockpit reports `not-owner` with the owner's port instead of running a second supervisor; three or more contenders over a stale lock, a mid-takeover error and a filesystem without hard links are documented residuals in its header. The default router is created only when an `apiKeyHelper` exists (`Router off: no apiKeyHelper` otherwise). **Watch-only:** a superagent worker session refuses every non-GET session action and `DELETE /api/sessions/:id` with 403 `ERR_WATCH_ONLY`, and answers the ws input types (`input`, `queue-remove`, `queue-reorder`, `queue-send-now`, `delegate`, handled in `src/ws-input.js`) with a `{ type: 'cockpit:watch-only', error }` frame instead of acting on them, because input would become part of the attempt the code then judges; `server.js` derives `isSupervisorOwned` (pilot or superagent, gates attach-token) and `isWatchOnly` (superagent only) from the host. **Routes:** `src/routes/superagent.js` (`GET /api/superagent`, job detail, `POST` job create/answer/accept/stop, artifacts read through `src/superagent/artifacts.js`'s real-path containment); `/api/notifications` now lives in `src/routes/notifications.js` and merges auto-pilot entries with superagent's (key `superagent:<jobId>:<needsYouSeq>`, from `src/superagent/notifications.js`), each source caught on its own, plus `superagentReady` (`host.notificationsReady()`: true only once `supervisor.start()` has resolved); while it is false the browser keeps `superagent:` keys in `cockpit:notifiedKeys` (`planNotifications`'s `keep`), so a restart never re-notifies. An answer must carry the `needsYouSeq` it was written for (accept may): `answerQuestion`/`accept` refuse a stale one with 409 `ERR_INVALID_STATE` before appending. A superagent bell entry or notification focuses an open Superagent tab and `postMessage`s it the job (`cockpit:superagent-select`) rather than reloading it; inside that tab it just selects the job. `src/superagent/view-model.js` shapes jobs for the view, and `createJob` refuses the same repo twice (`ERR_DUPLICATE_REPO`). A `COCKPIT_HOME` long enough on Windows makes every job fail with `ERR_PATH_TOO_LONG`. `tests/superagent-view-fixture.manual.mjs` seeds a temp `COCKPIT_HOME` and proves it launches nothing before any Cockpit runs on it.

`src/json-store.js` underneath all of this is `settings-file.js`'s atomic write (tmp + rename, Windows unlink-first), corrupt-file refusal and per-path serialized read-modify-write, extracted so cockpit's own files get the same guarantees a project's `settings.local.json` already had. `settings-file.js` keeps its API and delegates. Use `updateJson` when the payload is mutated in place and a corrupt file must be refused; `replaceJson` when it is rebuilt wholesale and a corrupt file must be replaced (that is `runtime.json`, where refusing would silently stop recording PIDs).
